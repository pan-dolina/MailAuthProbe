# Contributing to MailAuthProbe

Thank you for your interest in improving MailAuthProbe. Bug reports, test
cases from real-world mail and fixes are all welcome.

## Before you start

- For bugs, open an issue with the command you ran, the output (`--json` is
  most useful) and, if possible, a minimal message or DNS zone that
  reproduces it. Remove personal data from messages first.
- For new checks or behaviour changes, open an issue first so we can agree on
  the finding ID, severity and category.
- Security vulnerabilities must be reported privately; see
  [SECURITY.md](SECURITY.md).

## Development setup

Requirements: Go 1.26 or newer, Git, and a POSIX shell for the scripts.

```sh
git clone https://github.com/pan-dolina/MailAuthProbe
cd mailauthprobe
go test ./...
```

No test needs Internet access. Protocol tests use the in-memory zone from
`internal/dnsresolver/dnstest`; CLI tests start a local DNS server.

To try the CLI against the fixture zone:

```sh
go run ./internal/tools/testdns -addr 127.0.0.1:5353 &
go run ./cmd/mailauthprobe domain test.example --resolver 127.0.0.1:5353
```

## Quality gate

Pull requests must pass:

```sh
gofmt -l .                        # no output
go vet ./...
go test ./...
go test -race ./...
go run honnef.co/go/tools/cmd/staticcheck@v0.8.1 ./...
go run github.com/securego/gosec/v2/cmd/gosec@v2.29.0 -quiet ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...
scripts/check-dependencies.sh
```

## Guidelines

- **Layers.** Keep networking (`dnsresolver`, MTA-STS fetch), parsing,
  validation, findings and rendering separate. Protocol packages return data
  and findings; they never print.
- **Findings.** New rules go in `internal/findings/catalog.go` with the next
  free ID for the component. IDs are never renumbered or reused. Regenerate
  the catalog documentation with `go test ./internal/findings -update`.
- **Hostile input.** Anything read from a message, DNS or HTTP is untrusted.
  Bound every loop and allocation that depends on it, and never panic.
  Parser changes need a table test and, for new parsers, a fuzz target.
- **Tests.** Prefer table-driven tests. Message fixtures are generated by
  `go run ./internal/tools/fixturegen`; do not edit them by hand. After an
  intentional output change, update golden files with
  `go test ./test/functional -update` and review the diff.
- **Dependencies.** Avoid new modules. If one is necessary, explain why in
  `docs/development.md` and add it to `.github/allowed-modules.txt`.
- **Documentation.** Significant design decisions get an ADR in
  `docs/adr/`. Notable problems and their fixes go in the development journal.
- **GitHub Actions.** Pin actions to a full commit SHA with the version in a
  comment, and grant the minimum `permissions`.

## Commits and pull requests

- Use [Conventional Commits](https://www.conventionalcommits.org/)
  (`feat:`, `fix:`, `test:`, `docs:`, `ci:`, `build:`, `security:`, `perf:`,
  `chore:`).
- Keep each commit a single logical change that builds and passes tests.
- Add an entry under `[Unreleased]` in `CHANGELOG.md` for user-visible
  changes.
